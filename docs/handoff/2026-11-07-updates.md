# Numbered updates (2026-11-07)

Every push to `main` that changes the app is now a release, *Update N*: version `2.N`, annotated tag `v2.N`, and a
GitHub Release. The same notes appear, folded away, at the bottom of Settings next to *Check for updates*. Updates stay
silent: they download in the background and go in when the app is next left (see fb638b2 and 701670a for why).

## Where things live
- `scripts/release.mjs` covers the numbering, the notes and publishing. Its pure parts are tested in `tests/release.test.js`.
  - **The record is the annotated tag.** Its message lists the notes plus `Release-Date:` and, when urgent,
    `Release-Urgent: yes`. History is read back with `git for-each-ref`, so no API is needed and a local build after
    `git fetch --tags` gets the same history.
  - **N is the last tag's number plus one**, but only when a commit since that tag touches shipped paths (anything
    except `docs/`, `tests/`, `supabase/`, `.github/` and `*.md`). Otherwise the build is the last release again, byte for
    byte: the worker's build id is `r<N>-<hash of dist>`, not a timestamp.
  - **Notes** come from the merged PR's `## Release notes` / `## What's new` / `## Summary` top-level bullets (found
    through the GitHub API in CI), or else each commit's subject. As a commit trailer (or a line of its own in a PR body), `Release-Note: <text>` replaces the note,
    `Release-Note: none` drops it, and `Update: urgent` sets the release's `minimum`: a phone below it installs the
    update as soon as it has it, not when the app is next left.
  - `RELEASE_NUMBER=7 npm run build` forces a number. Use it for testing only.
- `vite.config.ts` (the `mustanir-release` plugin) puts the release in four places:
  - `__RELEASE__` in the app;
  - `virtual:release-history`, which only the Settings chunk imports;
  - `dist/sw.js` (`RELEASE`, `BUILD`, the precache list);
  - `dist/version.json`, the live release plus its history.
- `public/sw.js` answers `{type: "VERSION"}` on a MessagePort, so the app knows what a *waiting* worker is without the
  network. It leaves `version.json` and `sw.js` to the network.
- `src/lib/update.js` has the client rules, which are the old main.jsx block plus these:
  - `updateViaCache: "none"`;
  - a check on `pageshow` (restored from the back-forward cache), every 30 min while open, and on `online`;
  - a `version.json` read every 6 h;
  - if the site is ahead but the browser found nothing, a refetch of `sw.js` past the HTTP cache (Safari);
  - *Restart now*, with a 6 s fallback reload;
  - urgent releases;
  - an install record in localStorage `a2-release` (the "New" pill for 3 days).

  It never unregisters the worker: that would drop the push subscription.
- `src/components/updates.jsx` is the Settings section.
- `.github/workflows/deploy.yml`:
  - the build checks out with full history and tags, and gets `GITHUB_TOKEN` and `RELEASE_SINCE` (the commit main
    was on before the push, used for the very first release);
  - main runs queue instead of cancelling each other;
  - after deploy, the `release` job tags the release, publishes the GitHub Release and comments "Shipped in Update N"
    on the PRs it included.

## Verified
- All 62 tests pass under Node with the bun shim (memory `tests-without-bun`), including the 17 new ones.
- Build: a rebuild of the same commit gives an identical `sw.js`.
- In the browser, built and served from `dist`:
  - Update 5 checked as up to date.
  - After building Update 6 underneath it, *Check for updates* found it and showed "Update 6 is ready" with its notes
    under *Available*. *Restart now* landed in Update 6 with the "New" pill.
  - After building Update 7, a reopen put it in place by itself. It took about 30 s after the load, which is the known
    stall, and it then waited for the next reload rather than reloading mid-use.
